Be ready for this question

“If your data is synthetic, what have you actually learned?”

Three answers, all defensible. First, the synthetic nature was discovered, not assumed — Week 4 recovered the generating formula from the data with R² 0.999162, which is itself a result. Second, the geography is real: cities, coordinates and 840 road distances come from GeoNames and OSRM, so the distance sub-model is trained on observed data. Third, the project states explicitly which numbers are measurements of real skill and which are measurements of formula recovery — that distinction is Part 12 of this report and the reason two accuracy figures are quoted rather than one.

Why “no missing values” was itself a clue

A real-world dataset of 1,140 road trips with zero missing values, zero duplicates and perfectly consistent dtypes is unusual. At the time this was recorded as a convenience. In Week 4 it became evidence: datasets this clean are usually generated. Noticing it early and testing it later is the honest version of the story.

The insight hiding in this table

fuel_price correlates only +0.145 with cost, which looks unimportant. But fuel is the largest single cost, and the real fuel bill is litres × price. Price appears weak on its own because it only matters as a product with litres — and a linear model can only add its features, never multiply them. Week 6 turns this observation into the project's biggest single accuracy gain.

Part 4 · Week 2Data preprocessing — all eight steps

Week 2 followed the standard 8-step preprocessing checklist. Each step is given below with what was done, why, and what changed.

Step 1 — Understand the data

Re-ran shape, head() and info() to confirm the starting point: 1,140×16, no nulls.

Step 2 — Handle missing values

Counted nulls per column both as a count and as a percentage. Result: zero missing in all 16 columns. No imputation was needed, so none was invented.

What would have been done otherwise: numeric columns → median (robust to outliers, unlike the mean); categorical columns → mode; a column missing more than about half its values → drop it rather than fabricate it. Being able to state the policy you would have used matters more in a viva than the fact that this dataset needed none.

Step 3 — Remove duplicate rows

df.duplicated().sum() = 0 before and after drop_duplicates(). Shape unchanged at 1,140×16.

Step 4 — Fix data types

Printed df.dtypes and explicitly searched for columns stored as text that ought to be numeric or dates. Result: none. The six text columns are genuinely categorical.

Step 5 — Handle outliers

Boxplots were drawn for all ten numeric columns, then the IQR rule was applied to each in turn:

IQR = Q3 − Q1   ·   keep rows where   Q1 − 1.5×IQR  ≤  x  ≤  Q3 + 1.5×IQR
MeasureValue
Rows before outlier removal1,140
Rows after outlier removal1,129
Rows dropped11 (0.96%)

Boxplots were redrawn afterwards to confirm the extreme values were gone. Losing 11 rows out of 1,140 is a cheap price for removing points that would otherwise drag a least-squares fit.

An honest caveat on this step

The filter is applied column by column in a loop, so a row is dropped if it is extreme on any single column. That is stricter than a multivariate outlier test and it is applied before the train/test split, which technically lets information about the test rows influence which rows exist. With 11 rows out of 1,140 the effect is negligible, but the correct order in a strict pipeline is split first, then fit any data-dependent transformation on the training half only. Weeks 9 and 10 do exactly that for scaling — see Part 14.

Step 6 — Encode categorical columns

A model needs numbers. The six text columns were one-hot encoded with pd.get_dummies(..., drop_first=True).

ItemValue
Columns encodedstart_city, destination_city, vehicle_type, fuel_type, traffic_level, weather_condition
Shape after encoding1,129 rows × 31 columns (from 16)
MethodOne-hot, because none of these categories is ordinal

Why one-hot and not label encoding. Label encoding would map Hatchback→0, Sedan→1, SUV→2, which tells the model that an SUV is “twice” a Sedan and that Sedan sits exactly between the other two. None of that is true. One-hot gives each category its own independent column and asserts no ordering. drop_first=True removes one column per group to avoid the dummy variable trap — if you keep all three vehicle columns they sum to 1 in every row, which is perfectly collinear with the intercept.

Step 7 — Scale numeric columns

distance_km runs into the hundreds while passengers is 1–5. Features on wildly different scales distort distance-based and gradient-based methods, so MinMaxScaler mapped every numeric feature into 0–1:

x' = (x − xmin) / (xmax − xmin)

Nine columns were scaled: distance_km, mileage, fuel_price, passengers, departure_hour, toll_cost, parking_cost, estimated_time_minutes, fuel_consumption_litres.

One deliberate decision worth quoting

The target was left unscaled. That means every learned coefficient reads directly as “rupees of cost per unit of this feature”, and because the features are all on 0–1, a weight is literally “how many rupees the cost changes as this feature moves from its minimum to its maximum”. Scaling the target would have made the model equally accurate and completely unreadable.

Why MinMax and not StandardScaler? Standardisation (subtract mean, divide by standard deviation) assumes a roughly Gaussian spread and produces unbounded values. MinMax gives a bounded 0–1 range, which suits gradient descent — all partial derivatives end up on a comparable scale, so a single learning rate works for every weight.
