Part 13The application — API, frontend, tests, deployment

13.1 What happens on one prediction

This is the whole system in one sequence. Worth being able to narrate.

POST /api/predict  { start_city, destination_city, vehicle_type, fuel_type,
                     departure_hour, month, passengers,
                     mileage?, fuel_price?, parking_cost?, traffic_level? }

 1. resolve_city()        city name -> (state, lat, lon), largest city wins on ambiguity
 2. road_distance_km()    try LIVE OSRM routing
                          on failure -> sub-model 1 (distance model)
 3. predict_traffic()     sub-model 6: hour + month -> Low / Medium / High
                          (skipped if the user supplied traffic_level)
 4. default_mileage()     sub-model 2: vehicle + fuel -> km/l
                          (skipped if the user supplied mileage)
 5. fuel_price_for()      per-state lookup table; a user-supplied price always wins
 6. predict_litres()      sub-model 3: distance + mileage + traffic -> litres
 7. predict_toll()        sub-model 4: distance -> Rs
 8. DEFAULT_PARKING       sub-model 5 FAILED, so the training mean is used
 9. cost_model_chained    the chained regressor totals it
10. predict_band()        cost-band classifier -> Excellent / Good / Average / Poor
11. warnings[]            extrapolation, estimated fuel price, routing fallback
12. breakdown             fuel / toll / parking / wear-and-tear, by subtraction

The design decision worth defending: you are only asked what you could know

The model's strongest feature is fuel_consumption_litres at correlation +0.96. It would be trivially easy to build a form that asks for it — and the resulting product would be useless, because nobody knows how many litres they will burn before they set off. The same is true of toll and, for most people, their car's exact mileage.

So the form asks for two city names, a vehicle, a fuel type and a time. Everything else is predicted. That choice is why the honest accuracy is R² 0.9645 rather than 0.9997 — and it is the right trade, because the 0.9997 version could not be used by a real person.

Two things the API deliberately does not hide

  • The fuel price is prefilled but editable. The per-state table is verified for only 6 of 35 states. Anyone filling their own tank knows the real figure better than an estimate does, so a supplied value always wins and is reported as source: "user" — which correctly suppresses the estimated-price warning, because with a real figure there is nothing left to caveat.
  • Warnings are attached per prediction. Beyond 1,500 km the response says it is extrapolating. If OSRM was unreachable, it says the distance came from the model. If the fuel price was an estimate, it says so and invites the user to override it.

The departure sweep — expected cost, not argmax cost

Worth understanding because it is the one place a classifier's probabilities are used rather than its label:

E[cost | hour] = ∑levels P(level | hour) × cost(level)

Taking the single most likely traffic level would collapse 24 hours onto 3 distinct values and throw away everything the model knows about its own confidence. Weighting by probability gives a smooth curve where an hour that is 55% High reads differently from one that is 95% High.

13.6 Deployment

A two-stage Dockerfile: Node compiles the React app, then the Python image serves both the API and the built site, so one container runs everything. render.yaml describes the service for Render's free tier; the health check is /api/health.

  • Single worker, deliberately. The models and the 3,739-city table load per process, and the OSRM distance cache is in-process. Extra workers multiply memory and cold routing calls for no gain at this traffic level.
  • The image is lean. .dockerignore excludes the notebook, raw CSVs, scripts, tests, frontend source and the two large evaluation-only model files — only app.py, roadtrip_features.py, two small data files, the two served models and the built site ship.
  • Hosts that inject $PORT (Render, Railway, Fly, Cloud Run) are handled; it defaults to 8000 otherwise.
  • Free tiers sleep. Render's free instance spins down when idle and the first request after that takes ~30 s.

Stated plainly: the Docker build has not been executed — Docker is not installed in the development environment. The --outDir override the image depends on was verified directly, but expect to iterate once on the first real build. Saying this is better than implying it was tested.

Part 14Bugs found in this project's own code, and limitations

These are worth reading closely. An examiner who asks “what went wrong?” is offering the easiest marks in the viva, and a project that can name its own mistakes reads as far more credible than one that reports only successes.

14.1 Five real bugs, and how each was caught

1. The error bar next to every prediction was unachievable

FieldDetail
Symptom/api/predict returned typical_error: 39.66 beside every estimate.
CauseThat was the MAE of the cost regressor measured with the true toll, parking and litres handed in as features. A user supplies none of them, so no real prediction could ever achieve it.
FixIt now reports the chained pipeline's own held-out MAE, ₹391.16, plus a note saying most of it is toll and parking.
Guardtest_the_error_bar_beside_a_prediction_describes_that_prediction asserts it tracks the served figure and exceeds the fed-components one.

This was the single least honest thing in the project. It is also the most instructive: the model was never wrong, the reporting was.

2. The model-selection rule compared R² with a relative tolerance

FieldDetail
Symptompick_best chose a Ridge fit at 53.7 km RMSE over a random forest at 46.6 km — 15% worse — because the Ridge fit had a marginally steadier CV score.
CauseIt treated two models as tied if their R² was within 0.5% relative. Near R² = 0.99 that band is enormous in error terms.
FixCloseness is now judged on the error (2% of the best RMSE, or 0.5 accuracy points), then the one-standard-error rule decides, then simplicity.

3. The scaler leaked test-set information into training

FieldDetail
SymptomNone visible — which is what makes it dangerous.
CauseMinMaxScaler was fitted on the whole matrix before train_test_split, so test-set minima and maxima influenced the transformation applied to the training data.
FixEvery model is now wrapped in Pipeline([MinMaxScaler, model]), so cross-validation re-fits the scaler on each training fold and no validation-fold information reaches it.
Scale of the problemSmall for MinMaxScaler on this data — but it is exactly the mistake cross-validation exists to catch, so it was fixed rather than excused.

4. A 227 MB model file

FieldDetail
Symptommodels/pipeline.joblib came out at 227 MB, replacing a 10 KB file. The end-to-end benchmark was 546 MB.
CauseA 300-tree RandomForest fitted to 20,000 rows pickles to about 210 MB, and almost all of it was distance_dataset_model — a model used only inside the offline evaluation.
FixCompression alone was not the answer. The right question was which models does the API actually load? Splitting the evaluation-only models into a separate, git-ignored file and compressing both gives 5.1 MB served — a 44× reduction.

5. pandas 3 broke scikit-learn's cross-validation

FieldDetail
SymptomTypeError: only integer scalar arrays can be converted to a scalar index, thrown from inside cross_val_score.
Causepandas 3 stores text columns as Arrow-backed arrays (ArrowStringArray), and those do not support the fancy indexing (y[train_idx]) that scikit-learn performs internally.
FixOne helper, evaluation.labels(), converts label columns to a plain NumPy object array once, so every call site is correct rather than being debugged per model.

14.2 Limitations, stated plainly

  1. The wide dataset is generated, not observed. It is physically consistent with the original data — same recovered formula, real geography, real coordinates — but it is not independent evidence. The exception is data/real_distances.csv: 840 genuinely observed road distances, which is what the distance sub-model is trained on.
  2. The generated geography is off by 6.3% per route. The wide dataset sets distance_km = haversine × N(1.2355, 0.082). Against the 840 real routes that is nearly unbiased in the mean (−0.4%) but wrong by 6.3% on a typical single route. Costs measured on that dataset stay self-consistent, but the distance model is deliberately trained on the real data instead.
  3. Fuel prices: 6 of 35 states verified, 29 estimated. No free, current, machine-readable state-wise feed exists for India; three candidate sources were checked and rejected (one stale, one paid, one JavaScript-only). The CSV records which is which per row, the API warns when a prediction uses an estimate, and the user can override it.
  4. The rush-hour traffic profile was injected deliberately. In the original data traffic is statistically independent of departure hour — all five classifiers land on exactly the 50.88% majority baseline. The generator adds a realistic profile, so the traffic classifier's 57.0% measures that design choice, not Indian roads.
  5. Parking is not predicted, because it cannot be. Six model families all scored test R² ≤ 0, so the training mean is served. Roughly ₹50 of the reported error bar is this term alone.
  6. The error bar is large, and that is the honest number. MAE ₹391, of which about ₹529 of the ₹596 RMSE is irreducible noise in the generated data. Only the fuel-bill term could be improved by a better model.
  7. Predictions beyond 1,500 km extrapolate. The model was trained on 50–1,500 km; the API returns an explicit warning outside that range rather than silently guessing.
  8. Routing depends on a public demo server. OSRM's free instance is rate-limited and makes no uptime promise. Distances are cached and fall back to the fitted distance model, and distance_source says which was used.
  9. Travel time is not modelled. TRAFFIC_MIN_PER_KM remains a constant, deliberately: time is not part of the cost target, so fitting it would be inventing scope. It is labelled in the source rather than hidden.
  10. The Docker build has not been run. See Part 13.6.
