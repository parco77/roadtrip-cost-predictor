The one thing to remember before a viva

This project reports two accuracy figures, and knowing why is the whole point of it.

R² = 0.999707 is real, but it was measured with the true toll_cost, parking_cost and fuel_consumption_litres handed to the model as input features. Those are three of the four terms of the cost formula, and a traveller knows none of them before setting off. It answers “given the litres burnt and the toll paid, can you total the bill?”

R² = 0.9645, MAE ₹391 is what the model achieves predicting from what a user actually knows: two city names, a vehicle, a fuel type and a departure time. That is the number the deployed application reports, and the honest one to quote.

A note on how to read the tables

Wherever a model is scored, the report gives train and test figures side by side, plus a cross-validation mean and standard deviation. A single test score can be luck; the CV standard deviation is what says whether a model is stable. Wherever a constant was replaced by a model, the constant is kept in the table as the baseline row — a model that cannot beat the thing it replaced has not earned its place.

Part 1The project at a glance

1.1 The problem

Road trips involve several variable costs — fuel, tolls, parking, wear on the vehicle — which depend on the route, the vehicle, traffic conditions and how far you are driving. Estimating that total in advance is useful for planning and budgeting.

ItemValue
Problem statementGiven the details of a road trip, predict the total trip cost using machine learning.
Target variabletotal_trip_cost — continuous, in rupees
Problem typeRegression (a continuous numeric value). Two classification tasks were added in Week 7 where they add value.
Original datasetroad_trip_data.csv — 1,140 rows, 16 columns, 9 fixed city pairs
Final serving domainAny two of 537 Indian cities (population ≥ 100,000), 50–1,500 km

1.2 What the finished thing does

The user picks two cities, a vehicle, a fuel type and a departure time. They are asked only for things they could actually know. Everything else — road distance, their car's fuel efficiency, litres burnt, toll, traffic level — is predicted by its own fitted sub-model, and a chained cost regressor totals them. The response carries a full cost breakdown, an efficiency band, an honest error bar, and the caveats that apply to that particular prediction.

Why there is a shared roadtrip_features.py at the project root

Every model is trained in scripts/ and served from app.py. If those two built their feature vectors independently they would drift — a column reordered in one place and not the other gives predictions that are wrong but not obviously wrong. So each model has exactly one function that returns its features in a fixed order, and both sides call it. It sits at the project root rather than in scripts/ because the Docker image excludes scripts/, so the API could not import from there.
