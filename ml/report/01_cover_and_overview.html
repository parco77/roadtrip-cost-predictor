The one thing to take from this report

It reports two accuracy figures, and knowing why is the whole point of it.

R² = 0.999778 is real, but it was measured with the true toll_cost and fuel_consumption_litres handed to the model as input features. Those are the two terms that carry the uncertainty in the total, and a traveller knows neither before setting off. It answers “given the litres burnt and the toll paid, can you total the bill?”

R² = 0.9816, MAE ₹292 is what the model achieves predicting from what a user actually supplies: a distance, a fuel price and a parking figure. That is the number the deployed application reports, and the honest one to quote.

A note on how to read the tables

Wherever a model is scored, the report gives train and test figures side by side, plus a cross-validation mean and standard deviation. A single test score can be luck; the CV standard deviation is what says whether a model is stable. Every model is also shown against a baseline row — the simplest thing that could stand in its place. A model that cannot beat that has not earned its slot, and one of them does not.

Part 1The project at a glance

1.1 The problem

Road trips involve several variable costs — fuel, tolls, parking, wear on the vehicle — which depend on the route, the vehicle, traffic conditions and how far you are driving. Estimating that total in advance is useful for planning and budgeting.

ItemValue
Problem statementGiven the details of a road trip, predict the total trip cost using machine learning.
Target variabletotal_trip_cost — continuous, in rupees
Problem typeRegression (a continuous numeric value). Two classification tasks were added in Part 11 where they add value.
Original datasetroad_trip_data.csv — 1,140 rows, 16 columns, 9 fixed city pairs
Final serving domainAny two of 537 Indian cities (population ≥ 100,000), 50–1,500 km

1.2 What the finished thing does

The user types how far they are driving, what fuel costs where they are, and what they expect to pay for parking. Back comes a price for a hatchback, a sedan and an SUV at once, on all three fuels, each with a full cost breakdown, an efficiency band, an honest error bar and the caveats that apply to that particular estimate.

They are asked only for things they could actually know. Everything else — the litres they will burn, the tolls they will pay, and the km/l each vehicle manages — is predicted by its own fitted sub-model, and a chained cost regressor totals them. Distance is the one lookup, and the site ships a table of measured road distances between 139 cities so it is not a lookup the user has to do elsewhere.

1.3 Every model in this project, and what it does

Eight fitted things carry the product. Five are sub-models that supply a quantity the user cannot, one is the regressor that totals them, one is the label on each result, and one is a method demonstration rather than a served model. Part 10 scores all of them; this table is the map.

ModelIn → outFamilyWhat it is for
Distance four coordinates → road km RandomForest regressor Answers the distance lookup for any city pair the shipped table does not carry, and whenever live routing is unreachable. The only model here trained on observed rather than generated data.
Mileage vehicle + fuel → km/l Linear regression Gives each of the three vehicles its own fuel efficiency. One typed figure cannot be honest for a hatchback and an SUV at once, and the gap between the three is most of the gap between their costs.
Litres distance + mileage → litres Linear regression How much fuel the trip burns. Its fitted slope sits above the textbook distance ÷ mileage, because real driving costs more than the rated figure.
Toll distance → ₹ Linear regression The toll bill. Close to a per-km rate, but fitted and carrying its own error bar rather than asserted as a constant.
Parking — none — it failed Six model families were fitted and every one scored worse than predicting the mean. That negative result is why parking is the one cost the form asks for outright.
Cost (chained) the four above + what you typed → ₹ Linear regression The headline. Trained on its sub-models' predictions rather than on ground truth, so training and serving see the same kind of input. Called three times per request, once per vehicle.
Cost band the cost terms → Excellent / Good / Average / Poor Logistic regression Is this trip cheap or expensive for its length? A quartile split of ₹/km, which is the one judgement the rupee figure cannot make on its own.
Gradient descent same fit, solved iteratively from scratch, NumPy only Not served. It solves the same regression as the closed form and is kept to show the two agree on predictions while disagreeing on weights — which is what an ill-conditioned problem looks like.

The shape of the thing: what is asked for, and what is derived

The user supplies four numbers — distance, fuel price, parking, passengers — and gets back a cost for a hatchback, a sedan and an SUV, on all three fuels, with a breakdown for each.

Everything else is predicted, and the split is deliberate. Distance is asked for because it is the one input a traveller can look up exactly; the site ships a table of measured road distances so they do not have to go elsewhere. Parking is asked for because nothing predicts it. Litres and tolls are never asked for, because nobody knows them before setting off — and litres is the cost model's single strongest feature, so requesting it would be handing the model its own answer.

That last point is the whole design. An input is only worth collecting if the user can actually answer it.

Why there is a shared roadtrip_features.py at the project root

Every model is trained in scripts/ and served from app.py. If those two built their feature vectors independently they would drift — a column reordered in one place and not the other gives predictions that are wrong but not obviously wrong. So each model has exactly one function that returns its features in a fixed order, and both sides call it. It lives in backend/ because that is the folder which deploys: the API imports it directly, and the training scripts in ml/ import that same file instead of carrying a copy.
